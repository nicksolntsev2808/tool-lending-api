# Tool Lending API

REST API для «библиотеки инструментов» на FastAPI + MariaDB. Позволяет вести список инструментов (дрель, шуруповёрт и т. д.), выдавать их людям на время и принимать обратно.

## Что внутри

- Python 3
- FastAPI
- SQLAlchemy 2
- MariaDB (драйвер PyMySQL)
- Uvicorn

## Структура проекта
```text
tool-lending-api/
├── app/
│   └── main.py
├── .env.example
├── requirements.txt
```

## Правила приложения

- Статус инструмента: `available` (свободен) или `lent` (выдан). Новый инструмент всегда `available`.
- Выдать можно только свободный инструмент. Дата возврата (`due_date`) не может быть в прошлом.
- Принять обратно можно только выданный инструмент.
- Удалить можно только свободный инструмент (вместе с историей его выдач).
- Просроченная выдача: не возвращена, а `due_date` уже прошла.

## API методы

### Проверка состояния
```bash
curl http://127.0.0.1:8060/health
```

### Добавить инструмент
```bash
curl -X POST http://127.0.0.1:8060/tools \
  -H 'Content-Type: application/json' \
  -d '{"name":"Дрель Bosch","category":"электро"}'
```

### Список инструментов (с фильтром по статусу)
```bash
curl http://127.0.0.1:8060/tools
curl "http://127.0.0.1:8060/tools?status=lent"
```

### Получить инструмент по ID
```bash
curl http://127.0.0.1:8060/tools/1
```

### Выдать инструмент
```bash
curl -X POST http://127.0.0.1:8060/tools/1/lend \
  -H 'Content-Type: application/json' \
  -d '{"borrower":"Иван","due_date":"2026-12-01"}'
```

### Принять инструмент обратно
```bash
curl -X POST http://127.0.0.1:8060/tools/1/return
```

### История выдач (фильтры: активные / просроченные)
```bash
curl http://127.0.0.1:8060/loans
curl "http://127.0.0.1:8060/loans?active=true"
curl "http://127.0.0.1:8060/loans?overdue=true"
```

### Удалить инструмент
```bash
curl -X DELETE http://127.0.0.1:8060/tools/1
```

## Задача: Docker Compose из трёх сервисов (MariaDB + app + nginx)

В репозитории нет ни `Dockerfile`, ни `docker-compose.yml`, ни `nginx.conf`. Их нужно написать самостоятельно. Снаружи должен быть доступен **только nginx**.

1. **Dockerfile** для приложения:
   - лёгкий образ Python с конкретным тегом (не `latest`);
   - сначала `requirements.txt` и установка зависимостей, потом `app/` (зачем такой порядок?);
   - запуск **не от root**;
   - запуск через `uvicorn app.main:app --host 0.0.0.0 --port 8060`.
2. **`.dockerignore`**: исключи `.env`, `.git`, кэш Python.
3. **Сервисы в `docker-compose.yml`:**
   - `db` — официальный образ `mariadb` с конкретным тегом;
   - `app` — собирается из твоего `Dockerfile`;
   - `nginx` — официальный образ `nginx` с конкретным тегом.
4. **Переменные окружения:** посмотри на странице образа `mariadb` на Docker Hub, какие переменные он ожидает для создания базы, пользователя и паролей (там есть отдельный пароль для root). Значения не хардкодь в `docker-compose.yml`, вынеси в `.env` (а в репозиторий добавь только `.env.example`). `DATABASE_URL` для `app` собери из этих переменных (хост — имя сервиса, драйвер — `pymysql`).
5. **Именованный volume** для данных `db`. Выясни, в какую директорию внутри контейнера MariaDB пишет данные.
6. **`healthcheck` для `db`.** В образе `mariadb` есть готовый скрипт для проверки (поищи его в документации образа). Подбери `interval`, `timeout`, `retries`, `start_period` и объясни себе, зачем нужен последний.
7. **`healthcheck` для `app`.** В `slim`-образе Python нет `curl`. Придумай, как проверить `/health` без него (подумай про сам Python или установку curl в образ), и оцени, что из этого лучше.
8. **Цепочка запуска через `depends_on` с `condition: service_healthy`:** `app` ждёт `db`, а `nginx` ждёт `app`.
9. **`nginx.conf`:** nginx принимает запросы на 80 порту и проксирует всё на `app` (в `proxy_pass` используй имя сервиса, а не IP). Конфиг подключи в контейнер как bind mount, только на чтение.
10. **Порты:** наружу проброшен только порт nginx (на хосте 8060 → в контейнере 80). У `app` и `db` ports быть не должно. Как тогда nginx достаёт `app`, и чем `expose` отличается от `ports`?
11. Для всех сервисов добавь `restart: unless-stopped`.
12. Подними всё командой `docker compose up -d --build`, проверь `docker compose ps` (у `db` и `app` статус `healthy`) и `docker compose logs`.
13. Проверь через `curl` (на порт nginx) все эндпоинты и правила:
    - выдай инструмент с `due_date` в прошлом (ошибка), потом с нормальной датой;
    - выдай тот же инструмент второй раз (ошибка);
    - попробуй удалить выданный инструмент (ошибка);
    - прими инструмент обратно, затем попробуй принять ещё раз (ошибка);
    - проверь фильтры `/tools?status=...` и `/loans?active=...`.
14. Проверь изоляцию: `curl http://127.0.0.1:8060/...` работает, а прямого доступа к `app` и `db` с хоста нет.
15. Данные должны переживать перезапуск: `docker compose down`, затем `docker compose up -d`.

### Troubleshooting (сделай намеренно и разберись по логам)

16. Остановить только базу: `docker compose stop db`. Что происходит с запросами к API, что показывает `docker compose ps` и как приложение переживает возвращение базы?
